## Existing MCP servers converge on explicit project binding

### WHAT

Researched the current MCP specification, Codex plugin behavior, and project-aware servers. Found an upstream Codex issue from 2026-08-11 that exactly matches Goldfish: plugin MCP servers launch in the plugin cache, receive no workspace variable or substitution token, and Codex does not advertise MCP Roots.

### WHY

Goldfish has spent six months adding heuristics around cwd, roots, registry recovery, and parent walking. The live cache misbinding proves the premise is wrong: a server process cwd is a launcher detail, not trustworthy project identity.

### HOW

Compared three primary implementations:

- The official filesystem MCP server accepts directories through startup arguments or Roots and fails initialization when neither exists.
- Serena uses `--project`, an explicit `activate_project` tool, or guarded `--project-from-cwd`; if no marker is found, it leaves the project inactive.
- The official git MCP server requires `repo_path` on every tool call.

MCP 2026-07-28 deprecated Roots and directs new servers toward tool parameters, resource URIs, server configuration, or environment variables. Therefore Goldfish should follow the explicit-parameter and activation patterns, not deepen Roots dependence.

### IMPACT

The recommended design is fail-closed binding: explicit `workspace` on a call or a first-class activation step establishes project identity; configured `GOLDFISH_WORKSPACE` remains valid; legacy Roots can remain opportunistic during its support window; cwd and registry can suggest candidates but cannot authorize writes. This prevents silent writes to plugin caches while preserving cross-client operation.
